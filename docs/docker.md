# Быстрый запуск Docker на сервере A6000

Эти команды выполняются на Linux-хосте с Docker Engine и NVIDIA Container
Toolkit. Если терминал уже открыт внутри арендованного контейнера PyTorch,
не создавайте вложенный Docker: используйте имеющийся Python и
`bash scripts/train-a6000.sh --resume --skip-fetch --minutes 60`.
Обновлённый пакет также содержит прогресс и кеш промежуточных результатов оценки.

## Уже обученный эксперимент

Сначала завершите предыдущий расчёт, если он ещё идёт вне Docker. Из папки
проекта на сервере:

```bash
bash scripts/docker-a6000.sh run --resume --skip-fetch --minutes 60
bash scripts/docker-a6000.sh logs
```

При первом вызове образ `photonika:a6000` собирается на базе
`pytorch/pytorch:2.5.1-cuda12.1-cudnn9-runtime`. PyTorch уже установлен в базе,
повторно через pip он не скачивается. Устанавливается только научная часть
зависимостей; фронтенд, Streamlit, API и тестовые пакеты не входят в цель
`train`. Библиотеки не устанавливаются при старте контейнера.

Следующие вызовы `run` используют существующий образ без сборки и pull.
Работающий контейнер с тем же именем повторно не запускается. Остановленный
контейнер этого проекта заменяется, данные сохраняются в папке проекта на
хосте. Папка монтируется по тому же абсолютному пути: пути в старом
`manifest.json` остаются применимыми. Проверки кода, источников данных и весов
по-прежнему выполняются; новая среда не обходит проверки совместимости.

Для первого обучения нового эксперимента:

```bash
bash scripts/docker-a6000.sh run --minutes 180
```

Если менялись зависимости или базовый образ, пересоберите его явно:

```bash
bash scripts/docker-a6000.sh build
```

Команды состояния и остановки:

```bash
bash scripts/docker-a6000.sh status
bash scripts/docker-a6000.sh stop
```

При необходимости задайте `PHOTONIKA_IMAGE`, `PHOTONIKA_CONTAINER` или
`PHOTONIKA_PYTORCH_IMAGE`. Базовый образ должен содержать PyTorch 2.5.1
для совместимости с проверенной серверной средой. Скрипт запуска не обращается
к реестру, если локальный образ уже существует. Для предварительной загрузки
сделайте `build` до начала ограниченного по времени расчёта.

## Что ускорено

- Слой PyTorch расположен до файлов требований: изменение зависимостей
  приложения больше не заставляет скачивать CUDA/PyTorch заново.
- BuildKit сохраняет кеш загрузок pip и npm между сборками.
- Научные, веб-, демонстрационные и тестовые зависимости разделены.
- В сборку передаются только нужные исходники и статические ресурсы.
- Тестовые PNG копируются из репозитория вместо повторной генерации при сборке.
- Обычный старт готового контейнера не выполняет установку или сборку.

Приёмы кеширования описаны в
[официальной документации Docker](https://docs.docker.com/build/cache/optimize/).
Кеш сохраняется на конкретном Docker-хосте; новый арендованный узел может
потребовать холодную загрузку многогигабайтной базы. Скорость такой загрузки
зависит от сети и провайдера. Изменение Dockerfile не ускоряет выдачу машины
и создание окружения в панели аренды до запуска наших команд.

## Веб-интерфейс

Один раз соберите и затем запускайте без пересборки:

```bash
docker compose build web
docker compose up -d --no-build web
```

CPU: `docker compose --profile cpu build web-cpu`, затем
`docker compose --profile cpu up -d --no-build web-cpu`.
Streamlit собирается отдельной целью `streamlit` через одноимённый профиль.

Для передачи образа на сервер без повторной сборки можно использовать
`docker save` / `docker load`; веса и экспериментальные данные передаются
отдельно. Сборка реального образа и её время на A6000 в этой сессии не проверялись.
